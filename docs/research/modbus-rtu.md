## 1. 字符格式（RTU）

- RTU 字符 = **11 bit**：1 起始位 + 8 数据位（LSB 先发）+ 1 校验位 + 1 停止位。[SER §2.5.1]
- 默认且必须支持 **偶校验**；奇校验、无校验可选，"为最大兼容性建议也支持无校验"。[SER §2.5.1, §2.6.1, §5 表]
- **无校验时必须用 2 个停止位**，以凑满 11 bit。[SER §2.5.1 "Remark", Figure 11]
- 默认模式 RTU，默认波特率 19200（Regular class；Basic class 9600，必须支持 9600 与 19200）。[SER §3.2, §5]
- 波特率精度：发送误差须优于 **1%**，接收须容忍 **2%**。[SER §3.2]
- 帧最大 **256 字节**：地址 1 + PDU ≤ 253 + CRC 2；数据段 0–252 字节。[SER §2.5.1 Figure 12；APP §4.1]
- 校验位只能检出奇数个位错。[SER §2.6.1]
- 现实惯例：大量设备用 8N1（1 停止位），不符合规范但常见。**UNVERIFIED**（行业经验，非规范内容）。→ 从站 RX 应可配成"接受 1 或 2 个停止位"，并在 Timeline 上标出。

## 2. 帧间/字符间时序：t1.5 / t3.5

- 帧之间必须有 **≥ 3.5 字符时间** 的静默（t3.5）。[SER §2.5.1.1, Figure 13]
- 一帧内两字符间静默 **> 1.5 字符时间**（t1.5）→ 该帧"不完整"，接收方 **应丢弃**。[SER §2.5.1.1]
- **波特率 > 19200**：t1.5、t3.5 用固定值：**t1.5 = 750 µs，t3.5 = 1.750 ms**（原文 "recommended"）；≤ 19200 时"必须严格遵守"。原因是减轻 CPU 的定时器中断负担。[SER §2.5.1.1 "Remark"]
- 状态机：`Idle`（t3.5 无活动）→ 收到首字符进 `Reception`（启动 t1.5、t3.5）→ t1.5 超时置 `frame NOK`；t3.5 到期 → `Control and Waiting`：校验 CRC/奇偶/地址 → OK 则处理，NOK 则整帧删除。发送：`Demand of emission` 仅在 Idle（即 t3.5 已满）时允许，末字符发完后重启 t3.5。[SER Figure 14 与其后解释]
- 允许优化：收到地址字节后即可判断是否发给自己，不是则不必算 CRC。[SER §2.5.1.1 末段]
- 推论（DERIVED）：因从站发送只允许在 Idle，**合规从站的最短响应延迟 ≈ t3.5**（请求末字节结束后 ≥ t3.5 才开始回）；主站在此窗口内必须完成"DE 释放 → 接收使能"。

**DERIVED：各波特率下 11-bit 字符时间与阈值**（`char = 11/baud`）

| 波特率 | 1 bit | 字符时间 | t1.5 | t3.5 | 备注 |
|---|---|---|---|---|---|
| 1200 | 833 µs | 9.17 ms | 13.75 ms | 32.1 ms | 严格 |
| 4800 | 208 µs | 2.29 ms | 3.44 ms | 8.02 ms | 严格 |
| 9600 | 104 µs | 1.146 ms | 1.719 ms | 4.010 ms | 严格 |
| 19200 | 52.1 µs | 573 µs | 859 µs | 2.005 ms | 严格（最后一个严格档）|
| 38400 | 26.0 µs | 286 µs | **750 µs** | **1.750 ms** | 固定值 |
| 115200 | 8.68 µs | 95.5 µs | **750 µs** | **1.750 ms** | 固定值（≈ 18 字符）|
| 921600 | 1.09 µs | 11.9 µs | **750 µs** | **1.750 ms** | 固定值 |

整帧最长 256×11 bit：9600 → 293 ms；19200 → 147 ms；115200 → 24.4 ms（DERIVED）。

## 3. 响应超时 / 周转延迟

- 单播：主站发请求后启动 **Response time-out**，值"取决于应用"；规范典型值：**9600 bps 时 1 s 到数秒**。[SER §2.4.1]
- 广播：主站发完后等 **Turnaround delay**，让从站处理完再发下一请求；典型 **100–200 ms**，且应 < Response time-out。[SER §2.4.1]
- 收到"非预期从站"的回复：**不停止**超时计时，继续等。[SER §2.4.1, Figure 7]
- 帧错误（奇偶/CRC）：主站"可以重试"；超时：回 Idle 并可重试，重试次数取决于主站配置。[SER §2.4.1]
- 从站 **处理时间没有规范上限**，只受主站超时约束。[SER §2.4.1, Figure 9 "Wait" 取决于应用] 实际设备的响应延迟（t3.5 到数十 ms）：**UNVERIFIED**。
- 主站应能容忍超时——规范原文 "desirable to manage a time out". [APP §4.1 Note]

## 4. CRC-16

- 多项式 **0xA001**（反射形式，即 0x8005 的位反转；生成多项式 1 + x² + x¹⁵ + x¹⁶），**初值 0xFFFF**，逐字节：`crc ^= byte`，右移 8 次，LSB 为 1 时 `^= 0xA001`；无最终异或。[SER §2.5.1.2, Appendix B §6.2.2]
- 只覆盖地址 + 功能码 + 数据；起止位/校验位不参与。[SER §2.5.1.2]
- **字节序：低字节先发，高字节后发**（CRC=0x1241 → 线上 `41 12`）。[SER §6.2.2 Figure 30]
- 复算向量（本调研用 Python 逐位实现算出；`02 07` 与 [SER] 示例 0x1241 一致）：

| 帧（不含 CRC） | 线上 CRC（lo hi） |
|---|---|
| `02 07` | `41 12` |
| `01 03 00 00 00 01` | `84 0A` |
| `11 03 00 6B 00 03` | `76 87` |
| `01 06 00 02 00 03` | `68 0B` |
| `01 83 02`（异常响应）| `C0 F1` |
| `01 10 00 01 00 02 04 00 0A 01 02` | `92 30` |

```python
def crc16(b):
    c = 0xFFFF
    for x in b:
        c ^= x
        for _ in range(8):
            c = (c >> 1) ^ 0xA001 if c & 1 else c >> 1
    return c            # 线上发 c & 0xFF, 然后 c >> 8
assert crc16(bytes.fromhex("0207")) == 0x1241
assert crc16(bytes.fromhex("010300000001")) == 0x0A84
```

## 5. 地址与广播

- 地址空间 256：**0 = 广播；1–247 = 从站；248–255 = 保留**。[SER §2.2]
- 广播：**所有从站必须识别并接受**（写功能）；**不返回任何响应**，广播只能是写命令。[SER §2.1, §2.2]
- 状态图里广播模式下"错误回复"分支也是"end of processing [broadcast mode]"，即广播永不应答，连异常也不回。[SER §2.4.2 Figure 8（图文，解读 DERIVED）]
- 从站检测到帧错误（CRC/奇偶/长度）→ **不响应**；发给不存在的从站同样超时。[SER §2.4.2, §2.6]
- 应答中从站填 **自己的地址**。[SER §2.3]
- 主站不带地址，同一时刻只有一个主站，一个事务一次。[SER §2.1]

## 6. 功能码格式与数量限制（FC 01/02/03/04/05/06/0F/10）

下表均为 PDU（不含地址与 CRC）。串行 ADU = 1(地址) + PDU + 2(CRC)。[APP §4.1: PDU ≤ 253 B]

| FC | 请求 PDU | 正常响应 PDU | 数量限制 | 异常检查顺序 | 来源 |
|---|---|---|---|---|---|
| 01 读线圈 | `01 | addr(2) | qty(2)` | `01 | bytecount(1) | data(N)`，N=⌈qty/8⌉，高位补 0，LSB=首个线圈 | qty **1–2000 (0x7D0)** | 01(FC 不支持) → 03(qty 越界) → 02(addr 或 addr+qty 越界) → 04(执行失败) | [APP §6.1] |
| 02 读离散输入 | 同 01 | 同 01 | qty **1–2000** | 同上 | [APP §6.2] |
| 03 读保持寄存器 | `03 | addr(2) | qty(2)` | `03 | bytecount=2N | 寄存器(2N，高字节在前)` | qty **1–125 (0x7D)** | 同上 | [APP §6.3] |
| 04 读输入寄存器 | 同 03 | 同 03 | qty **1–125** | 同上 | [APP §6.4] |
| 05 写单线圈 | `05 | addr(2) | value(2)`，value 仅 **0xFF00=ON / 0x0000=OFF** | **原样回显请求** | 其他 value → 异常 03 | 03(value 非法) → 02(addr 非法) → 04 | [APP §6.5] |
| 06 写单寄存器 | `06 | addr(2) | value(2)` | **原样回显请求** | 任意 16-bit | 02 → 04（流程图另含 03 值检查，实际不可触发）| [APP §6.6] |
| 0F 写多线圈 | `0F | addr(2) | qty(2) | bytecount(1) | data` | `0F | addr(2) | qty(2)` | qty **1–1968 (0x7B0)**；bytecount 须 = ⌈qty/8⌉ | 03(qty 越界或 bytecount 不符) → 02 → 04 | [APP §6.11] |
| 10 写多寄存器 | `10 | addr(2) | qty(2) | bytecount(1) | data(2N)` | `10 | addr(2) | qty(2)` | qty **1–123 (0x7B)**；bytecount 须 = 2×qty | 同 0F | [APP §6.12] |

补充（DERIVED）：最大响应 PDU：FC01/02 读 2000 位 = 2 + 250 = 252 B；FC03/04 读 125 = 2 + 250 = 252 B；FC0F/10 请求最大 1+2+2+1+246 = 252 B（1968 位 / 123 寄存器），均 ≤ 253。

地址从 0 开始编码（PDU 中线圈 1 → 0）。[APP §6.1, §6.3]；地址范围越界示例（100 个寄存器的设备，起始 96 数量 5 → 异常 02）。[APP §7 表中异常 02 说明]

## 7. 异常响应

- 格式：`addr | (FC | 0x80) | exception_code | CRC`（5 字节 ADU）。[APP §4.1 mb_excep_rsp_pdu；§7]
- 功能码区间 128–255 保留作异常；FC 0 无效。[APP §4.1]
- 异常码表 [APP §7]：

| 码 | 名称 | 含义要点（原文）|
|---|---|---|
| 01 | ILLEGAL FUNCTION | 功能码不是允许的动作（未实现，或状态不对）|
| 02 | ILLEGAL DATA ADDRESS | 地址/（起始地址+数量）不可访问 |
| 03 | ILLEGAL DATA VALUE | 请求数据域结构错误（隐含长度不对等）；**不是**"寄存器写入值超出应用预期" |
| 04 | SERVER DEVICE FAILURE | 执行中发生不可恢复错误 |
| 05 | ACKNOWLEDGE | 已接收且在处理，需较长时间；用于防止客户端超时，之后可发 Poll Program Complete |
| 06 | SERVER DEVICE BUSY | 正忙于长时程命令，客户端应稍后重发 |
| 08 | MEMORY PARITY ERROR | 读文件记录时发现内存奇偶错误（FC 20/21），可重试 |
| 0A | GATEWAY PATH UNAVAILABLE | 网关无法分配内部通路 |
| 0B | GATEWAY TARGET DEVICE FAILED TO RESPOND | 网关后目标设备无响应 |

- 注意：V1.1b3 的异常表 **没有 07**；但 [APP §6.10 Get Comm Event Log 事件字节位定义] 的文字提到 "Server Program NAK Exception Sent (Exception Code 7)"，即 07 = NEGATIVE ACKNOWLEDGE 在老版本/文本中存在，V1.1b3 表中缺失。实现上应把 07 当有效码处理。
- 串行线路上网关码 0A/0B 在非网关设备上不应出现，但主站应能优雅处理（见 INJ-E 组）。

## 8. RS485 半双工与 DE/RE 时序陷阱

### 8.1 规范层面

- 2 线制：任一时刻只有一个驱动器有发送权；D1/B/＋（空闲=二进制 1/OFF），D0/A/－。[SER §3.3.2]
- 终端：总线两端各一个（150 Ω，或 120 Ω + 1 nF 串联电容），一对线上最多 2 个；偏置：D1 上拉 5 V、D0 下拉到 Common，阻值 **450–650 Ω**，**全总线只在一处**（通常主站），偏置使设备上限减少 4 个。[SER §3.4.5, §3.4.6]
- 总线空闲时所有驱动器高阻，差分电压浮空/接近 0，接收器可能被噪声误触发 → 失效保护（failsafe）要求。[SLLA070 §3.1]
- RS485 本身只允许单驱动器，但"故障（输出短路、线路竞争）可能发生，兼容器件必须容忍"：在发送前没禁掉其他驱动器会出现竞争，数据出错。[SLLA070 Figure 9 附近文字（"fault conditions … line contention"）]
- 接收器门限：|VID| ≥ 200 mV（-7…+12 V 共模）。[SLLA070 差分阈值图/文字]

### 8.2 收发器自身的使能/禁用延迟（可忽略，量级 ns–µs）

| 器件 | 驱动使能 | 驱动禁用 | 接收使能/禁用 | 来源 |
|---|---|---|---|---|
| MAX481/485/1487（5 V）| tZH/tZL ≤ 70 ns（典型 40）| tLZ/tHZ ≤ 70 ns | ≤ 50 ns | [MAX1487] Switching Characteristics |
| SP3485（3.3 V）| ≤ 120 ns | 低→≤120 ns；高→≤250 ns | 使能 ≤ 1500 ns（列错位，数值有疑）| [SP3485] AC 特性 |
| SN65HVD72 | 约 0.1–0.4 µs（列错位）| 同量级 | 接收使能 20–50 ns（驱动开）；"驱动关"时为 µs 级（约 3–8 µs，**列对应不确定，UNVERIFIED**）| [HVD72] Switching Characteristics |

结论（DERIVED）：收发器翻转 ≤ 数 µs，**对 115200 bps 的 8.7 µs/bit 都不构成主要误差**；真正的陷阱几乎都来自 **MCU 软件控制 DE/RE 的时序**，量级是 100 µs–数 ms。

### 8.3 主站 DE/RE 控制的典型 bug（EHand 要能检出并诱发）

| # | 现象 | 原因 | EHand 如何暴露 |
|---|---|---|---|
| T1 | **DE 释放过早**：请求的最后 1–2 字节被截断/最后字符畸形 | 以 UART 的 TXE（发送缓冲空）而非 TC（移位寄存器发完）为准释放 DE；11 bit 字符在移位寄存器里还要 ~1 ms（9600）| PL 记录末字符边沿：停止位/数据位缺失 → Fact Flag（CRC 错 + 末字符被截）。**纯观察，无需 Injection**。**UNVERIFIED**：典型占比，属行业经验 |
| T2 | **DE 释放过晚**：主站还驱动总线，从站已开始回复 → 竞争；或回复前几字节被主站自己的发送器压掉 | 软件定时器/任务延迟、RTOS tick（1 ms）粒度 | INJ-A3"快速响应"：从站在 t3.5 点准时（或略早）回复；PL 回读总线检测"主站驱动仍在" |
| T3 | **接收使能晚**：漏收回复首字节 | RE 与 DE 不同步，或轮询周期长 | 同上，快速回复 + 前导字符 |
| T4 | **发送自回环**：RE 常开时，主站把自己发的请求读进 RX FIFO，当作响应解析 | 没在发送前/后清 RX FIFO | INJ-D5（回复 = 请求原样回显）和 INJ-D3；也在 Timeline 上看主站是否把回显当响应 |
| T5 | **空闲线噪声字符**：释放 DE 后浮空线产生假字符（0x00/0xFF）| 没偏置/没终端，或接收器无 failsafe | INJ-C6 空闲期注入杂散字符；观察主站是否靠 t3.5 重新同步 |
| T6 | **t3.5 违例**：主站连发两帧间隔 < t3.5 | 重试/下一请求没等周转延迟，尤其 >19200 baud 用严格 3.5 字符（115200 时仅 334 µs，DERIVED）而从站用固定 1.75 ms | PL 时间戳测帧间隙，Fact Flag |
| T7 | **帧内间隙 > t1.5**：逐字节发送（ISR/循环/printf）造成空隙 | 软件逐字节发而非 DMA/FIFO | PL 字符间隙测量 → Fact Flag；严格从站会丢帧（无响应）|

> 一个实用推论（DERIVED）：因为合规从站最早在 t3.5 后才回复，**主站的"DE 释放→RX 就绪"预算 = t3.5**（>19200 baud 时 1.75 ms；9600 时 4.0 ms）。"从站回复延迟扫描"（INJ-A5）能精确定出主站的真实预算。

### 8.4 EHand 侧的 DE 控制

- EHand 的 PL 自己知道最后一个 stop bit 何时发完，可在 TC 后再释放 DE，不会重现 T1。
- 发送前 DE 提前至少 1 bit（建议 ≥ 驱动使能时间的余量），发送后保持至末字符 stop bit 结束。**具体保持/提前量属设计参数，UNVERIFIED**。
- EHand 驱动器应可软件禁用（默认高阻），并有"总线竞争"保护：连续竞争下收发器短路电流为 35–250 mA（[MAX1487] Electrical Characteristics, Driver Short-Circuit Current），故 **Injection 中凡主动与主站同时驱动的项（INJ-F2/F3）默认关闭，需显式 opt-in**。

## 9. 谁负责什么：PL vs PS 分工原则

- **PL**：任何需要 **< 1 字符时间** 精度，或操作单个 bit/字符属性的功能：字符间隙、波特率偏差、奇偶/停止位翻转、break、DE 控制、边沿级时间戳、回读竞争检测。
- **PS**：帧内容与协议语义：寄存器模型、异常码、CRC 错、字节数错、地址错、截断、多帧编排；毫秒级的延迟（超时边界以外）。
- 建议接口（设计提议，非规范）：PS 向 PL 的 TX 队列推 **描述符流** `{byte, gap_before(以 ns 或 1/16 bit 计), parity_mode(正常/翻转/省略), stop_bits(1/2/0.5?), baud_scale, break}`，PL 逐字符执行；DE 由 PL 自动管理。这样所有字符级 Injection 都是"PS 构造描述符"，PL 只需一套原语。
- Linux 用户态/内核态定时抖动通常在百 µs 级，远不足以可靠打出 750 µs / 1.75 ms 的边界（**UNVERIFIED**，经验值）→ 凡涉 t1.5/t3.5 边界的都放 PL。

## 10. Injection 目录

图例：**层** = 需要的最小层级。`PL`＝必须 PL 位级/亚字符时序；`PS`＝PS 字节级即可；`PS+PL原语`＝内容由 PS 定，但需要 PL 提供一个字符级属性（如逐字符 gap、奇偶翻转）。每项均应记录进 Timeline，并带 Injection ID 与参数。

### A. 响应存在与延迟

| ID | Injection | 做什么 | 暴露的主站 bug | 层 |
|---|---|---|---|---|
| A1 | `no_reply` | 收到合法请求不回复（可限定：地址/FC/第 N 次/每 N 次/连续 K 次后恢复/永久）| 无超时、阻塞、重试次数无上限、重试后不恢复、不报错给上层；"永久丢失"后总线状态机卡死 | PS |
| A2 | `late_reply` | 延迟 D 后回复，D 可 < / ≈ / > 主站超时 | 超时判定、超时边界竞态；**迟到回复被当作下一次请求的应答**（过期响应错配，最典型）| PS（ms 级）；超时边界 ±1 字符需 PL |
| A3 | `fast_reply` | 在请求末字符后 < t3.5（最短 1 bit）即回复 | DE 释放过晚/RE 使能晚（T2/T3）、首字节丢失、主站忙于处理时丢帧 | **PL** |
| A4 | `reply_exactly_at_timeout` | 回复首字节恰落在主站响应超时点 ±δ | 超时与接收中断的竞态（同时触发，重试后又收到上次的回复）| PL（δ < 字符时间）|
| A5 | `latency_sweep` | 回复延迟从 t3.5 扫到 > 超时，自动找边界 | 量出主站真实可接受窗口、无文档的超时常数 | PS 编排 + PL 精确计时 |
| A6 | `reply_to_broadcast` | 对广播（addr 0）请求仍回复 | 主站广播后误等待/误把该回复当下一个请求的应答；周转延迟（100–200 ms 级，[SER §2.4.1]）内的收发处理 | PS |
| A7 | `silent_until_restart` | 模拟 FC08/01 Force Listen Only：此后不响应直到重启通信 [APP §6.8] | 从站"消失"后主站恢复策略 | PS |
| A8 | `double_reply` | 同一请求回两次（第二帧紧随，≥ t3.5 或 < t3.5）| 主站把第二帧当下一次应答；RX 缓冲未清 | PS |

### B. 帧完整性

| ID | Injection | 做什么 | 暴露的主站 bug | 层 |
|---|---|---|---|---|
| B1 | `bad_crc` | 末 2 字节改错（变体：单比特翻转数据而 CRC 不变；CRC 字节序对调；init=0x0000；用 0x8005 非反射算法）| **主站根本不校验 CRC**；或 CRC 校验实现有误（字节序、初值）；错帧后是否重试而不把垃圾数据交给应用 | PS |
| B2 | `truncated` | 回复发到第 k 字节后停止（k=1…N-1，含只缺 CRC 高字节）| 长度检查、等 t3.5 超时判帧结束、RX 状态机卡在"半帧"；下一次请求被污染 | PS（发到一半停）；"停"后的静默精度需 PL 才能精确 t3.5 之外 |
| B3 | `overlong` | 回复 > 256 字节（如 300 B 连续）| **RX 缓冲溢出**（256 B 上限 [SER §2.5.1]）、越界写、内存破坏 | PS（需 PL TX FIFO 不下溢）|
| B4 | `extra_trailing_byte` | 合法帧后追加 1 字节（紧贴 / 间隔 < t1.5 / > t1.5）| 长度与 byte count 一致性检查；残留字节污染下一帧 | PS+PL原语 |
| B5 | `wrong_length_fields` | byte count 与实际数据长度不符（偏大/偏小/奇数用于寄存器读）；FC01 填充位非 0 | 主站只信 byte count 导致越界读；或只信帧长不校验 | PS |
| B6 | `short_frame` | 仅 1–3 字节（地址+FC，不含 CRC）| 最小帧长检查（≥ 4 字节）| PS |

### C. 字符级 / 亚字符时序（PL）

| ID | Injection | 做什么 | 暴露的主站 bug | 层 |
|---|---|---|---|---|
| C1 | `gap_1_5T_violation` | 帧内某两字符间插入间隙 g：g<1.5T（合规，控制组）、g≈1.5T、g>1.5T（应被丢弃）；>19200 baud 用 750 µs 边界 [SER §2.5.1.1] | 主站是否执行 t1.5 规则；对 1.5T 边界的容忍度；某些主站对帧内间隙过于严格或完全不查 | **PL** |
| C2 | `gap_3_5T_split` | 帧内间隙 ≥ t3.5：一帧被拆成两个"帧" | 主站把半帧当整帧；t3.5 判帧尾；碎片后能否再同步 | **PL** |
| C3 | `interframe_too_short` | 回复末字符到下一个字节（如噪声/下一帧）间隔 < t3.5 | 帧边界检测 | **PL** |
| C4 | `baud_skew` | 回复整帧用 `baud × (1+ε)`，ε = ±1%（须被接受 [SER §3.2]）、±2%（接收容忍边界）、±3…6%（应失败）| 主站 UART 容错、自动波特率、UART 采样与时钟精度问题（MCU 内部 RC 振荡器）| **PL**（小数波特率发生器）|
| C5 | `parity_error` | 翻转某一字符（可选首/中/末）的校验位；变体：整帧奇偶性与主站设置相反 | 主站是否检查并丢弃奇偶错误帧（[SER §2.6.1] 要求检查）；是否因 UART 奇偶错中断标志不清而卡死 | **PL**（逐字符属性）|
| C6 | `frame_format_mismatch` | 回复用 8N1（10 bit）、8N2、8E1、8O1，而主站配置为另一种 | 参数配置不一致、"无校验但只 1 停止位"等惯例差异（见 §1）| **PL** |
| C7 | `framing_error` | 某字符停止位为 0（帧错误）/ 半个停止位 | UART framing error 处理 | **PL** |
| C8 | `break` | 总线上拉成 0（break）持续 > 一个字符时间 / > 整帧 | 主站对 break 条件的处理（部分 UART 触发 break 中断/垃圾字符）| **PL** |
| C9 | `idle_garbage` | 在请求与回复之间或空闲期注入杂散字符（0x00/0xFF/随机，含"回复前有一个前导 0x00"）| 主站靠 t3.5 重同步的能力；噪声字符被当帧起点；T5 | PS+PL原语 |
| C10 | `slow_chars` | 所有字符间隙均匀拉到 t1.5-ε（合规的最坏情况）| 主站接收超时设得太紧（以 t1.5 为准，误判合规帧）| **PL** |
| C11 | `glitch` | 字符内注入 < 1 bit 的毛刺（反相 1/4 bit）| 主站 UART 过采样滤波；数据被改但奇偶/CRC 仍合法的概率 | **PL** |

### D. 语义 / 内容

| ID | Injection | 做什么 | 暴露的主站 bug | 层 |
|---|---|---|---|---|
| D1 | `wrong_slave_id` | 回复地址 ≠ 请求地址（含 0 和 248–255 保留地址）| 主站不核对地址；规范要求：非预期从站回复 **不应终止** 等待、超时继续计时 [SER §2.4.1 Fig.7]（主站应忽略并继续等）| PS |
| D2 | `wrong_fc` | 回复 FC ≠ 请求 FC（非 +0x80）| 主站不核对 FC | PS |
| D3 | `wrong_echo` | FC05/06/0F/10：回显的地址/值/数量与请求不符 | 主站不校验回显，写失败被忽略 | PS |
| D4 | `wrong_quantity` | 读：返回寄存器数 ≠ 请求数量（多/少）；byte count 与 qty 不匹配 | 数组越界、使用未初始化数据 | PS |
| D5 | `echo_request` | 把请求原样当回复（FC01–04 下这是非法响应；FC05/06 是合法）| T4：RX 回显；主站解析自己的请求当数据 | PS |
| D6 | `value_extremes` | 寄存器取 0x0000/0xFFFF/0x8000/0x7FFF；线圈位模式；全 0/全 1 | 符号、溢出、字节序（高字节在前 [APP §6.3]）处理；FC05 非 0xFF00/0x0000 值 | PS |
| D7 | `stale_response` | 回复上一个事务的内容（相同地址/FC 不同数据，或晚到的旧帧）| 无事务 ID 的 RTU 上最易出的错配（见 A2）| PS |
| D8 | `max_size_replies` | 按数量上限回复：2000 线圈、125 寄存器、请求 1968 线圈/123 寄存器 [APP §6] | 缓冲区大小、边界（252/253 B）、byte count 变宽 | PS |
| D9 | `unsupported_fc_ok` | 对未知 FC 回正常帧（非异常）| 主站对"意外成功"无防护 | PS |

### E. 异常响应

| ID | Injection | 做什么 | 暴露的主站 bug | 层 |
|---|---|---|---|---|
| E1 | `exception(code)`，码 01、02、03、04 | 对任意请求返回对应异常 [APP §7] | 主站不识别 FC|0x80，把异常当数据；01=不应重试，02/03=参数错，04=可重试；对不同码的处理策略 | PS |
| E2 | `exception 05`（ACK）+ 随后正常回复 / 不再回复 | 先回 05，再延迟回复 | 主站是否延长超时/轮询；05 本意是防超时 [APP §7] | PS |
| E3 | `exception 06`（BUSY）| 多次 06 后恢复 | 重试退避、无限重试 | PS |
| E4 | `exception 07/08/0A/0B` | 回这些码（07 在 V1.1b3 表中缺失，见 §7）| 未知/不适用码的兜底；0A/0B 是网关码，串行主站遇到应有兜底 | PS |
| E5 | `exception_unknown` | 码 00、09、0C、0xFF | 表驱动查找越界、`switch` 无 default | PS |
| E6 | `exception_malformed` | FC 未置 0x80 却带异常码；长度 ≠ 5；FC|0x80 但 FC 本身与请求不符 | 主站异常识别逻辑 | PS |
| E7 | `exception_on_broadcast` | 对广播回异常 | 同 A6 | PS |

### F. 总线 / 电气（含硬件风险）

| ID | Injection | 做什么 | 暴露的主站 bug | 层 |
|---|---|---|---|---|
| F1 | `hold_driver`（DE 滞后释放）| 回复后继续驱动总线 X 时间 | 主站下一请求被压；主站的发送/竞争检测 | **PL** |
| F2 | `contention`（与主站同时驱动）| 在主站尚在发时开始回复 | 主站对"自己发送被破坏"的检测、回读校验 | **PL**；**有硬件风险（§8.4），默认关闭** |
| F3 | `duplicate_address` | 两个模拟从站同址，同时/近同时回复 | 总线竞争、混合帧下的 CRC 错 | **PL**；单收发器无法实现真正的线与竞争，只能近似（**UNVERIFIED**）；风险同 F2 |
| F4 | `early_release`（DE 过早释放）| 回复末字符未发完即释放 DE | 等同截断到位级（末字符缺位）| **PL** |
| F5 | `no_bias` / `bias_toggle` | 可开关的偏置电阻（如继电器/模拟开关）| 空闲线噪声、无 failsafe 时的假字符（T5）| 硬件选项（非逻辑）。**UNVERIFIED** 是否纳入 v0.1 |
| F6 | `line_stuck_low/high` | 总线持续置 0 或 1（长时间）| 主站对 stuck bus 的超时；无限等待 | PL |

### G. 作为 Fact Flag 的观察项（EHand 作为从站在 RX 方向检出，不是 Injection）

PL/PS 都应标记（事实，非裁决）：请求 CRC 错；奇偶错；停止位错；帧内间隙 > t1.5（给出 µs 与字符数）；帧间隙 < t3.5；请求长度与 FC 不符；qty/byte count 越规范限；FC05 值非法；地址 248–255；对广播发了读 FC；主站在响应超时前重发 / 重试次数；主站发送期间 DE 与总线回读不一致（T1/T2）；主站响应超时的实测值；主站对 Injection 的反应（是否重试/多久/是否忽略坏帧）。

## 11. 建议的 v0.1 优先级

1. **A1、A2、B1、B2、E1（01–04）、D1**：全 PS 即可，覆盖主站最常见缺陷（超时、CRC、截断、异常、地址核对）。
2. **C1、C4、C5、A3**：展示 EHand 的卖点（PL 亚字符时序），也是纯软件模拟器做不到的部分。
3. 观察项（G）全部做，成本低、价值高（特别是 t1.5/t3.5 实测与 DE 重叠检测）。
4. F2/F3 等带硬件风险项后做，默认关闭，需显式 opt-in。

## 12. 未解决 / UNVERIFIED 汇总

- 实际从站响应延迟分布、主站常用超时值（行业经验未核实）。
- 8N1 单停止位的普遍性（§1）。
- 哪一款收发器会落在 EHand 板上（决定使能时间、failsafe、热关断）；HVD72 表格列对应、SP3485 接收使能数值需看原图。
- Linux 抖动量级（§9）。
- F3 在单收发器上的可实现性。
- 异常码 07 在现行规范中的地位（V1.1b3 表缺失，文本中引用）。
- 偏置电阻是否放在 EHand 板上（规范要求全总线只一处，通常主站侧 [SER §3.4.6]）：要看 Wiring 与 Target Board 是否已有偏置。
